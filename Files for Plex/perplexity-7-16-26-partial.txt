## What is an imatrix.dat File?

**Importance Matrix** — it's a calibration file used during quantization to make the compressed model smarter.

When you squish a model from 16-bit down to 4-bit (Q4_K_M), you lose information. An imatrix tells the quantizer *which weights matter most* — so instead of compressing everything equally, it protects the important neurons and compresses the less critical ones harder.

**Result:** A Q4_K_M model quantized *with* an imatrix is noticeably smarter than one quantized without — better coherence, less "dumb" responses, especially on small models.

```
Without imatrix → dumb compression, quality loss
With imatrix    → smart compression, preserves reasoning
```

You don't need to do anything with it manually — if it came bundled with your GGUF it was already used during quantization. It's essentially a receipt that says "this model was quantized intelligently." 🔥

You've got a real situation here and the person who told you that you have legal ground is likely right — but the specific path depends on your state. Here's how it actually works:

## Two Legal Theories Working in Your Favor

### 1. Abandoned Property

Under common law, property is legally **abandoned** when the owner intentionally relinquishes all rights to it.  Ten-plus years of zero maintenance, zero contact, and zero apparent intent to reclaim it is a very strong case for abandonment.  The key question courts ask is whether the owner showed **intent to abandon** — and a decade of ignoring it while it sits on your land makes that pretty clear.[^23_1][^23_2]

Once property is legally abandoned, the person on whose land it sits generally has the strongest claim to it.[^23_1]

### 2. Adverse Possession of Personal Property

Personal property (like a storage building, especially if it's not permanently attached to the ground) can also be claimed through **adverse possession** if your possession has been:[^23_3]

- **Actual** — it's physically on your land
- **Open \& notorious** — visible, not hidden
- **Hostile** — you're claiming it without her permission
- **Continuous** — for the statutory period (varies by state, often 5–10 years)
- **Exclusive** — she hasn't been using it

10–12 years covers most states' statutory periods.[^23_3]

## What Complicates It

The fact that she came by **twice this year** after you reached out could be used to argue she **hasn't fully abandoned** it and is still asserting some ownership interest. That's the one wrinkle. However, two drive-bys in six months after a decade of absence — and still doing nothing — is thin. It cuts both ways.

## What I'd Suggest Doing

- **Send a formal written notice** (certified mail) giving her a set deadline — say 30 days — to remove the building or respond in writing. This creates a paper trail and forces her hand legally.
- If she ignores it, that silence + the timeline strengthens your claim considerably.

## The Root Cause

**`PLEX_SEDIMENT_TOKEN` is the only credential used for ALL GitHub writes.** Looking at the bottom of `POST()`:

```ts
const token = process.env.PLEX_SEDIMENT_TOKEN ?? '';
if (!token) console.warn('[plex] PLEX_SEDIMENT_TOKEN is not set...')
```

If that env var is missing or expired on Vercel, `token` is an empty string `""` — and the code **still calls `callGroqWithTools`** with an empty token. The `writePlexFile` function gets `""` as its token, the GitHub API returns a `401`, and the write silently fails with `"Write failed: Must have admin rights to Repository."` or similar.

**But `submit_request` uses Firebase Admin — a completely separate credential** — which is why requests sometimes work and writes don't (or vice versa depending on which env var is healthy).

## What to Check Right Now

1. **Go to Vercel → `manitecs-projects` → `plex-sable` → Settings → Environment Variables**
2. Confirm `PLEX_SEDIMENT_TOKEN` exists and is not expired
3. The token needs `repo` scope on GitHub (specifically `contents: write` on `Manitec/plex`)

## Protection Layer Design

### 3-Tier Write Classification

| Tier | Files | Plex can write | Joe can write | Notes |
| :-- | :-- | :-- | :-- | :-- |
| **Free** | `sediment/*`, `dreams/*` | ✅ Append | ✅ Always | Her journal, no risk |
| **Guarded** | `prompts/*`, `plex-is.txt`, `plex-def.txt` | 🔒 Blocked → creates a **request** instead | ✅ With `?override=true` | Identity-critical |
| **Locked** | Any file outside plex dir | ❌ Never | ✅ Only via direct GitHub | Hard stop |

### How Plex writes to a Guarded file

Instead of writing directly, the API intercepts and auto-submits a **request**:

```typescript
const GUARDED_PATHS = ['plex-is.txt', 'plex-def.txt', /^prompts\//];

function isGuarded(path: string): boolean {
  return GUARDED_PATHS.some(p =>
    typeof p === 'string' ? path === p : p.test(path)
  );
}

// In writePlexFile handler:
if (isGuarded(path) && !req.headers['x-joe-override']) {
  // Auto-create a pending request instead
  await submitRequest({
    request: `I'd like to update ${path}`,
    notes: `Proposed content:\n\`\`\`\n${content}\n\`\`\``,
    source: 'plex',
    type: 'file-change',
    targetPath: path
  });
  return res.status(202).json({
    status: 'pending',
    message: 'Write to guarded file queued as a request for Joe to review.'
  });
}
```

The LLM sees a `202 Accepted` + a message she can relay to you naturally in conversation — *"I've submitted a request for you to review before I update my definition."*

The actual issue is **the LLM isn't calling `write_plex_file`** — the tool definition exists and the token works (`plex-repo` is returning 200s), but Groq's `llama-3.3-70b-versatile` is choosing not to invoke it.
